# ChangeProof Storage Handoff

## 1. Implementation Summary

This document records the completed implementation and verification of
the ChangeProof experiment storage platform.

The implementation provides:

-   Amazon S3 for experiment evidence artifacts.
-   Amazon DynamoDB for experiment metadata, workload runs, breaches,
    and measurements.
-   Terraform infrastructure as a separate platform stack.
-   A Python `boto3` storage layer.
-   Unit tests using `pytest` and `moto`.
-   A demo ingestion script.
-   AWS CLI verification steps.
-   A cleanup procedure for removing the demo infrastructure when it is
    no longer required.

## 5. DynamoDB Single-Table Design

Table:

``` text
changeproof-experiments
```

Billing mode:

``` text
PAY_PER_REQUEST
```

Primary key:

``` text
PK = string
SK = string
```

TTL:

``` text
ttl
```

TTL was verified as enabled in AWS.

### Item types

#### META

``` text
PK = EXP#<experimentId>
SK = META
```

The metadata record contains experiment state and investigation-level
information such as:

-   `experimentId`
-   `status`
-   `observedSeverity`
-   `predictedSeverity`
-   `predictionAccuracy`
-   `confidence`
-   `blastRadiusCount`
-   `changeSummary`
-   `changedAddresses`
-   `phase`
-   `telemetrySource`
-   `simulated`
-   `reason`
-   `evidenceKey`
-   timestamps
-   `ttl`

`verdict` is intentionally absent during initial experiment creation and
is added later when the investigation reaches the appropriate stage.

#### RUN

``` text
PK = EXP#<experimentId>
SK = RUN#baseline
```

or:

``` text
PK = EXP#<experimentId>
SK = RUN#changed
```

Run records contain workload configuration, fingerprint,
attempted/accepted/throttled/failed counts, achieved rate, time windows,
drain status, and notes.

#### BREACH

``` text
PK = EXP#<experimentId>
SK = BREACH#<resourceAddress>#<metric>
```

Breach records contain the resource, metric, actual value, limit, limit
kind, severity, and description.

#### METRIC

``` text
PK = EXP#<experimentId>
SK = METRIC#<resourceAddress>#<metric>
```

Metric records contain:

-   resource address
-   metric
-   resource type
-   unit where applicable
-   predicted low/high values
-   baseline value
-   observed value
-   actual change percentage
-   outcome
-   rule ID
-   `simulated`

## 6. Global Secondary Indexes

### GSI1

Purpose: query experiments by status.

``` text
GSI1PK = STATUS#<status>
GSI1SK = createdAt
```

The index uses an INCLUDE projection containing the required
investigation summary attributes.

DynamoDB automatically projects the index key attributes, so those key
attributes are not duplicated in `NonKeyAttributes`.

### GSI2

Purpose: query measurements by resource type and metric.

``` text
GSI2PK = METRIC#<resourceType>#<metric>
GSI2SK = createdAt
```

The index includes the required metric and observation attributes.

Again, the index key attributes are automatically projected and are not
duplicated in `NonKeyAttributes`.

## 7. Storage-Layer Behavior

The Python implementation is:

``` text
backend/storage/changeproof_storage.py
```

It uses `boto3` for AWS access.

Important implementation rules:

### Simulated flag

Every measurement-carrying META/METRIC record receives `simulated`
directly from the supplied observation.

The implementation does not silently assume or discard this value.

### Decimal conversion

Python floating-point values are recursively converted to:

``` python
Decimal(str(value))
```

This prevents DynamoDB `boto3` serialization problems with Python
`float`.

### Empty strings

Empty strings are recursively removed rather than being written to
DynamoDB.

### Progressive metadata

The META record is created before environment work and subsequently
updated as the experiment progresses.

### Verdict versus prediction accuracy

These fields are independent:

-   `predictionAccuracy` describes how well the prediction matched the
    observation.
-   `verdict` represents the resulting investigation decision/state.

They are not treated as the same field.

## 12. Cost Considerations

The platform intentionally avoids always-running compute.

DynamoDB uses:

``` text
PAY_PER_REQUEST
```

Therefore there is no provisioned read/write capacity sitting idle.
Charges are associated with actual requests and storage.

S3 has no always-running compute component. Costs are primarily
associated with storage, requests, and applicable data transfer.

The Terraform configuration does not enable DynamoDB Point-in-Time
Recovery, which avoids that optional charge.

The 30-day S3 lifecycle is intended to limit retained evidence.

The demo generated only a small amount of data. Actual AWS charges
depend on the AWS account's current pricing, free-tier eligibility,
credits, requests, and other resources in the account.

## 13. Cleanup

When the platform is no longer required, destroy it from the same
Terraform root:

``` powershell
cd C:\Users\vsiro\changeproof-aws\terraform\platform
terraform destroy
```

The S3 bucket is configured with `force_destroy = false`, so Terraform
will not automatically delete a non-empty bucket.

Before destroying the stack, empty the demo prefix:

``` powershell
aws s3 rm s3://<deployed-bucket-name>/experiments/EXP-DEMO-001/ --recursive --region ap-south-2
```

Then run:

``` powershell
terraform destroy
```

Review the Terraform plan carefully and type:

``` text
yes
```

Only destroy the platform if the stored experiment evidence is no longer
required.

## 14. Production Considerations

Before using this platform for production workloads, consider:

-   Restricting IAM permissions to the minimum required S3 and DynamoDB
    operations.
-   Adding CloudWatch monitoring and alarms where operational monitoring
    is required.
-   Defining retention requirements before selecting lifecycle periods.
-   Considering whether S3 Object Lock or additional audit controls are
    required for evidence that must be tamper-resistant.
-   Encrypting with a customer-managed KMS key if organizational
    requirements require it.
-   Adding backup/recovery requirements for DynamoDB if experiment
    records become business-critical.
-   Adding automated integration tests for GSI queries and
    lifecycle-related configuration.
-   Managing Terraform state in a protected remote backend rather than a
    developer workstation.
-   Keeping AWS credentials outside source control and using an
    appropriate IAM role or federated identity.
-   Reviewing the `simulated` flag carefully when mixing simulated and
    real observations.
